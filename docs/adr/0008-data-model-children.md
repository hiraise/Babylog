# ADR-0008: Несколько детей: таблица `children`, все записи в `events` с привязкой к ребёнку

- **Статус:** Принято
- **Дата:** 2026-10-15
- **Затрагивает:** `core/model/`, `core/data/`, `core/data/room/` (`Entities.kt`, `Migrations.kt`, `AppDatabase.kt`), `app/schemas/`
- **Заменяет:** [ADR-0004](0004-data-model.md)

## Контекст

В приложении ведут дневник нескольких детей (двойня, погодки). Записи всех типов устроены
одинаково: время, необязательное окончание, одна деталь и комментарий. Это невосстановимая
история, поэтому потеря данных — худший возможный дефект.

## Решение

- Дети хранятся в таблице `children` (`id`, `name`, `birthDate`). В базе всегда есть хотя бы
  один ребёнок: новая база создаётся с ребёнком «Малыш», последнего удалить нельзя.
- Имена детей уникальны без учёта регистра и пробелов по краям (`isNameTaken`): по имени
  дети сопоставляются в CSV.
- Все записи — в таблице `events` (`childId`, `type`, `startTime`, `endTime`, `detail`, `note`);
  `childId` — внешний ключ с `ON DELETE CASCADE`. Новый тип записи добавляй в эту таблицу,
  а не в отдельную.
- В коде запись — `BabyEvent` (sealed); перевод в строки `type`/`detail` и обратно — только
  в `EventRecord.kt`.
- Время — epoch millis, усечённые до секунды в репозитории (`truncatedToSecond()`) при каждой
  вставке и правке: CSV хранит секунды, без усечения дедупликация импорта не найдёт совпадений.
- Активный сон — `Sleep` с `end = null`, у ребёнка не больше одного (`DiaryRepository.startSleep`
  в транзакции). Таймер переживает перезапуск; сны разных детей идут независимо.
- Ребёнок удаляется вместе со своими записями и только после подтверждения с их числом.
- Выбранный на экране ребёнок хранится вне базы: `SelectedChildStore` (SharedPreferences).
- Схему меняй только повышением версии `AppDatabase` с `Migration`; JSON-схемы из `app/schemas/`
  храни в репозитории. `fallbackToDestructiveMigration` и миграции с потерей данных запрещены.

## Последствия

- Миграция 2→3 превращает прежний профиль в ребёнка «Малыш» (id 1) и привязывает к нему
  все записи; `id` и время записей не меняются.
- Новый тип записи не требует миграции.
- Значения деталей проверяются в коде (`EventRecord.toEvent`, диалоги), а не схемой БД.

## Проверка

- `scripts/dev.sh check` проходит.
- Миграцию проверяй установкой новой версии поверх старой с данными: `scripts/dev.sh db`
  до и после, записи должны совпасть.
