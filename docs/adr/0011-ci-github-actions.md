# ADR-0011: Проверки — в `scripts/dev.sh`, на GitHub Actions для каждого PR; `main` меняется только через PR с зелёным CI

- **Статус:** Принято
- **Дата:** 2026-10-16
- **Затрагивает:** `.github/workflows/`, `.github/dependabot.yml`, `scripts/dev.sh` (`rules`, `check`, `build`, `schemas`), CLAUDE.md «Сборка и проверка», README «Разработка»

## Контекст

Проект лежит на GitHub (`hiraise/Babylog`) и меняется AI-агентами, часто в параллельных сессиях.
Проверки должны работать одинаково локально и на сервере и не зависеть от того, помнит ли
агент правила. Сборка почти не тратит токены, а чтение кода ради сверки с правилами и
ручные проверки — тратят: их место в скрипте.

## Решение

- Держи логику проверок в `scripts/dev.sh`. Workflow только готовит окружение и вызывает
  команды скрипта. Новую проверку добавляй в скрипт, а не в YAML.
- Пиши скрипт так, чтобы он работал на macOS и Linux: bash и `grep -E` без GNU-расширений.
- `rules` — проверки без Gradle: дизайн-токены ([ADR-0010](0010-design-system.md)), правила из
  разделов «Проверка» ADR, которые ловятся поиском по коду, индекс ADR и ссылки в `.md`.
  Меняешь такое правило в ADR — меняй `check_adr_rules` в том же изменении.
- `check` = `rules` + `testDebugUnitTest lintDebug assembleDebug` — обязательная локальная проверка.
- CI (`.github/workflows/ci.yml`) на каждый PR и push в `main` выполняет `rules`, `build` (то же
  и `assembleRelease`) и `schemas` (сборка не изменила `app/schemas/`).
- CI работает на `ubuntu-24.04` с JDK 17 — нижней границей из [ADR-0006](0006-tech-stack-agp9.md).
- Подключай только открытые actions. Закрепляй их по SHA коммита с версией в комментарии.
  У `gradle/actions/setup-gradle` ставь `cache-provider: basic`: кеш по умолчанию проприетарный.
- Workflow проверок работает без секретов, с `permissions: contents: read`; не используй
  `pull_request_target`.
- Меняй `main` только через PR с зелёной проверкой «Проверка». Каждая задача — своя ветка;
  параллельные сессии работают в отдельных `git worktree`.
- Читай результат CI коротко: `gh pr checks`, при падении — `gh run view <id> --log-failed`.
- Обновления зависимостей и actions предлагает Dependabot (`.github/dependabot.yml`); Gradle,
  AGP, Kotlin и KSP — одной группой.

## Последствия

- Падение CI воспроизводится локально той же командой, что в шаге workflow.
- lint удлиняет локальную проверку; release-сборку и сверку схем локально запускают по желанию.
- Переезд на другую CI-платформу — новый YAML, скрипт остаётся.

## Проверка

- Каждая строка `uses:` в `.github/workflows/` содержит 40-символьный SHA.
- `grep -n cache-provider .github/workflows/ci.yml` показывает `basic`.

## Альтернативы

- Проверки в YAML — расходятся с локальными и привязывают проект к GitHub.
- Свой раннер на машине владельца — код из чужих PR выполнялся бы на личном компьютере.
- Renovate — гибче Dependabot, но для полутора десятков зависимостей это лишнее.
