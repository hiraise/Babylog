# ADR-0004: Единая таблица событий, время с точностью до секунды, схема меняется только миграциями

- **Статус:** Заменено [ADR-0008](0008-data-model-children.md)
- **Дата:** 2026-08-15 (записано 2026-10-15)
- **Затрагивает:** `app/src/main/java/com/kid/babylog/data/`, `app/schemas/`, `MainViewModel.kt`

## Контекст

Записи всех типов (кормление, подгузник, сон, лекарство, вес) устроены одинаково: время,
необязательное окончание, одна деталь и комментарий. Это невосстановимая история малыша,
поэтому потеря данных — худший возможный дефект.

## Решение

- Все записи хранятся в таблице `events` (`Event`: `type`, `startTime`, `endTime`, `detail`,
  `note`). Смысл `detail` зависит от `type` и описан в KDoc `Event`. Новый тип записи
  добавляй в эту же таблицу, а не в отдельную.
- Время — epoch millis, усечённые до секунды (`truncToSecond()` в `MainViewModel`) при каждой
  вставке и правке: CSV хранит секунды, и без усечения дедупликация при импорте не найдёт
  совпадений.
- Активный сон — запись `SLEEP` с `endTime = null`, одновременно не больше одной
  (`EventDao.startSleepIfNone` в транзакции). Поэтому таймер переживает перезапуск.
- Профиль малыша — единственная строка таблицы `profile` с `id = 1`.
- Схему меняй только повышением версии `AppDatabase` с `Migration`; JSON-схемы из
  `app/schemas/` храни в репозитории. `fallbackToDestructiveMigration` и любые миграции
  с потерей данных запрещены.

## Последствия

- Новый тип записи не требует миграции, но требует правок `EventType`, `CsvCodec.rowToEvent`,
  UI и README.
- Значения `detail` проверяются в коде (`CsvCodec.rowToEvent`, диалоги в `ui/Dialogs.kt`),
  а не схемой БД.
