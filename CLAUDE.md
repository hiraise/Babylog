# BabyLog — правила работы с проектом

«Дневник малыша» — открытое автономное Android-приложение для учёта режима малыша
(Kotlin, Jetpack Compose, Room). Проект разрабатывают AI-агенты (Claude). Правила ниже
обязательны: они держат контекст проекта под контролем.

## Принципы

Изменить принципы может только владелец проекта, и только новым ADR.

1. **Открытый и некоммерческий** ([ADR-0001](docs/adr/0001-open-source-non-commercial.md)).
   Лицензия — GPL-3.0-or-later; зависимости — только открытые и совместимые с ней.
   Никакой монетизации (реклама, платные функции, подписки, покупки), закрытых частей
   и шагов к приватизации.
2. **Автономный** ([ADR-0002](docs/adr/0002-standalone-local-data.md)). Всё работает без
   сети, данные хранятся только на устройстве. Своего сервера, аккаунтов, аналитики и
   трекеров нет. Сеть — только в интеграциях, которые пользователь включает сам: запросы
   к сервисам за информацией, бэкап в подключённое им хранилище и т. п.

## Где что описано

| Что | Где | Для кого |
| --- | --- | --- |
| Концепция, возможности, форматы данных, настройка интеграций, сборка | `README.md` | человек, затем агент |
| Архитектурные и системные решения | `docs/adr/` (индекс — `docs/adr/README.md`) | агент, затем человек |
| Устройство кода: пакеты, слои, как добавить функцию или тип записи | `docs/adr/0007-architecture.md` | агент |
| Правила работы | `CLAUDE.md` | агент |

- Каждый факт описан в одном месте; в остальных — ссылка, а не копия.
- Перед изменением прочитай индекс ADR и те ADR, у которых поле «Затрагивает»
  пересекается с задачей. Принятые ADR обязательны.
- Документация обновляется в том же изменении, что и код, а не «потом».

## Когда нужен ADR

ADR нужен, если изменение:

- добавляет или заменяет библиотеку, Gradle-плагин или часть стека;
- меняет модель данных или формат обмена: новые таблицы, смысл существующих полей,
  формат CSV или бэкапа;
- добавляет сетевое взаимодействие, интеграцию или permission в `AndroidManifest.xml`;
- меняет структуру модулей и пакетов или подход: DI, навигацию, работу с состоянием;
- меняет сборку и распространение: minSdk/targetSdk, подпись, CI, публикацию;
- касается безопасности и приватности данных: шифрования, секретов, разрешений;
- отменяет принятое решение или отступает от него.

ADR не нужен для исправления ошибок, правок UI, новых функций в рамках принятых решений,
рефакторинга без смены подхода и обновления версий без изменения поведения.

Если сомневаешься, проверь: может ли агент, который не знает об этом решении, нарушить его
или переизобрести по-другому? Если да — нужен ADR. Решение, о котором пользователь
не просил, сначала согласуй с ним (ADR со статусом «Предложено»).

## Как писать ADR

ADR читают прежде всего агенты, поэтому он короткий и проверяемый:

- шаблон — `docs/adr/template.md`; имя файла `docs/adr/NNNN-slug.md`, номер — следующий
  свободный, номера не переиспользуются;
- заголовок формулирует само решение («CSV — формат экспорта и импорта», а не «Про экспорт»);
- одно решение на ADR, около 40 строк; без истории обсуждений и пересказа кода — вместо
  них пути и идентификаторы в `обратных кавычках`, чтобы их находил поиск;
- «Решение» — проверяемые правила в повелительном наклонении, по одному на пункт;
- «Затрагивает» — пути и пакеты: по ним агент находит ADR для своей задачи;
- новый ADR сразу добавляется строкой в индекс `docs/adr/README.md`.

Принятый ADR по существу не переписывается. Чтобы изменить решение, напиши новый ADR
с полем «Заменяет: ADR-NNNN», а старому поставь статус «Заменено ADR-MMMM» (и в индексе
тоже). Опечатки и переехавшие пути исправлять можно.

## Когда обновлять README

README пишется для людей. Обнови его, если изменение заметно пользователю или разработчику:
возможности, формат CSV, сборка и отладка, интеграции. Для каждой интеграции в README
есть подраздел: что она делает; какие данные, куда и когда уходят с устройства; как её
включить и настроить; как отключить. Объяснение «почему так» — в ADR, README на него ссылается.

## Язык

Документация, ADR, комментарии в коде и интерфейс — на русском; идентификаторы и имена
файлов — на английском.

## Сборка и проверка

- Задача не считается выполненной, пока не проходит `scripts/dev.sh check` и не зелёный CI
  в её PR. `check` — правила проекта (`scripts/dev.sh rules`: дизайн-токены, правила ADR,
  ссылки в документации), unit-тесты со сверкой скриншотов, lint и debug-сборка; что проверяет
  CI — [ADR-0011](docs/adr/0011-ci-github-actions.md). Gradle нужен JDK 17+: если в `JAVA_HOME`
  Java ниже, скрипт сам возьмёт JDK из Android Studio.
- Изменения UI проверяй скриншот-тестами, миграции — тестами миграций, а не вручную
  ([ADR-0013](docs/adr/0013-jvm-android-tests.md)). Намеренно поменял вид — перезапиши эталоны
  `scripts/dev.sh goldens` и закоммить изменившиеся PNG; картинки при этом не открывай.
- Эмулятор — для того, что тестом не проверить (системный выбор файла, поворот, телефон):
  `scripts/dev.sh run|logcat|db|screenshot` (debug-сборка `com.kid.babylog.debug` с отдельной
  базой), подробности — README, «Локальная отладка».

## Ветки и PR

- Каждая задача — своя ветка от `main`. Параллельная сессия работает в отдельном worktree:
  `git worktree add ../kid-<задача> -b <ветка> main`, затем скопируй туда `local.properties`.
- В `main` изменения попадают только через PR (`gh pr create`). Сливает PR владелец, агент —
  только по его просьбе и при зелёном CI.
- Результат CI читай кратко: `gh pr checks`, при падении — `gh run view <id> --log-failed`.
  Упавший шаг повтори локально той же командой (`scripts/dev.sh rules|build|schemas`);
  полный лог не скачивай.
