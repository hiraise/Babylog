# Выпуск версии

Что такое релиз — [ADR-0012](../../../docs/adr/0012-release-signing.md): как поднимается версия,
куда ставится тег и что делает `release.yml`. Здесь — порядок действий агента. Правила
[AGENTS.md](../../../AGENTS.md) («Ветки и PR», «Сборка и проверка») действуют и тут.

Версия из аргумента: «$ARGUMENTS». Если её нет — следующая минорная после `versionName`
в `app/build.gradle.kts` (1.10 → 1.11). Ниже `X.Y` — эта версия, `N` — номер релизного PR.

Релиз — один PR `release/vX.Y`, в который влиты все готовые PR, а не цепочка PR по очереди.

## 1. Состав

1. `git fetch --prune origin`. Если ветка `release/vX.Y` или её PR уже есть — продолжай их,
   а не начинай заново.
2. Покажи владельцу открытые PR (`gh pr list --state open`) и спроси, какие войдут в релиз.
   Сам не выбирай: часть PR ещё в работе у других задач.

## 2. Релизная ветка

1. Работай последовательно в основной папке, без worktree. Перед переключением `git status`
   должен быть чист. Создай ветку от свежего `origin/main`:
   `git switch -c release/vX.Y origin/main`. Если ветка уже есть — `git switch release/vX.Y`,
   затем `git pull --ff-only`.
2. Влей выбранные PR по очереди, начиная с раньше открытого: `git merge --no-ff origin/<ветка PR>`.
   Ветки не переписывай (rebase, cherry-pick): тогда GitHub не отметит их PR слитыми.
   - Конфликт в PNG-эталонах `app/src/test/screenshots/` — возьми любую сторону; после всех
     слияний перезапиши эталоны `scripts/dev.sh goldens` и закоммить изменившиеся PNG.
   - Два PR с одним номером ADR — номер остаётся за PR, открытым раньше, а позднему ADR дай
     следующий свободный по [шаблону ADR](../../../docs/adr/template.md).
   - Остальные конфликты разрешай по смыслу обоих PR, спорное — спроси владельца.
3. Подними версию по ADR-0012 отдельным коммитом «Версия X.Y».
4. `scripts/dev.sh check` — зелёный.

## 3. Показ и PR

1. Собери релиз на общем эмуляторе (`scripts/dev.sh run` из основной папки), скажи
   владельцу, что вошло и что посмотреть, и дождись одобрения.
2. Опиши релиз во временном файле вне репозитория по образцу ниже и открой PR:
   `git push -u origin release/vX.Y`, затем
   `gh pr create --base main --draft --title "Версия X.Y" --body-file <файл>`.
   Черновик держи, пока владелец не скажет, что состав собран: в ветку ещё вливают PR.
   Сказал сразу «релизим» — открывай без `--draft`.
3. Описание меняй целиком из того же файла, а не заменой строки:
   `gh api -X PATCH repos/hiraise/Babylog/pulls/N -F body=@<файл>`.
   Удали временный файл после завершения работы с PR.

```markdown
Релиз X.Y (versionCode <новый>).

## Что входит

- #NN — <что заметит пользователь; крупный PR — подпунктами>
- …

<Совместимость: что версии до X.Y не прочтут в CSV или бэкапе — если такое есть.>

## Как выпустить

Слить обычным merge, не squash, и поставить тег `vX.Y` на коммит слияния — это делает
`.agents/skills/release/finish.sh X.Y`.

Проверка: `scripts/dev.sh check` на этой ветке зелёный.
```

## 4. Пока PR открыт

Работа идёт последовательно в основной папке проекта, без отдельного worktree.

- Начинай, только если `git status` чист. Чужие незакоммиченные правки значат, что там
  осталась другая задача: остановись и сообщи владельцу, не изменяй их и не запускай сборку.
- Затем `git pull --ff-only`, влей, `scripts/dev.sh check` и сразу `git push`, чтобы следующая
  задача начала с актуального состояния.
- Историю релизной ветки не переписывай (`commit --amend`, `reset`, `rebase`): последний коммит
  может быть чужим. Исправляй новым коммитом.
- Новый PR в состав — только по слову владельца, так же как в п. 2, и строкой в описании.

## 5. Выпуск

Когда владелец скажет, что состав собран:

1. `git fetch`. У каждого вошедшего PR не должно остаться коммитов вне релиза —
   `git log --oneline origin/release/vX.Y..origin/<ветка PR>` пуст. Иначе влей их, иначе
   GitHub оставит их PR открытым.
2. `gh pr ready N`, затем `gh pr checks N --watch`. Упал — `gh run view <id> --log-failed`,
   и чини в релизной ветке.
3. Слияние и тег делает [finish.sh](finish.sh). Если владелец запускает его сам, дай команду
   с абсолютным путём к скрипту в основной папке проекта:
   `bash <…>/kid/.agents/skills/release/finish.sh X.Y`.
   Если владелец просит сделать это тебя и разрешения пускают — запусти тот же скрипт сам.

## 6. После выпуска

1. Скрипт печатает ссылку на GitHub Release — передай её владельцу.
2. Проверь, что вошедшие PR отмечены слитыми: `gh pr view <номер> --json state`.
3. Переключись на `main`, обнови её и удали локальные ветки слитых задач. Worktree не используются.
